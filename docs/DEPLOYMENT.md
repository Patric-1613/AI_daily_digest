# Deployment provider options and free-tier operating plan

Last reviewed: 2026-09-10

This document records the delivery-provider evaluation for issue
[#53](https://github.com/Patric-1613/AI_daily_digest/issues/53). Pricing and free-tier limits
change independently of this repository, so the delivery owner must recheck the linked provider
pages before creating a resource or approving a cost.

This is an operational recommendation. The team has separately approved exactly one paid resource
— the `ai-daily-digest-intelligence` cron (see "Intelligence rehearsal cron") — and no other. It
is not authorization to create any further account, paid resource, production credential, or real
subscriber campaign. Secrets belong in the deployment provider's secret environment, never in Git,
issue comments, build output, or application logs.

## MVP recommendation

Use the following combination for the seven-day MVP:

| Capability | Provider and plan | MVP use |
|---|---|---|
| React/Vite frontend | Render Static Site, Free | Build and serve the static frontend. |
| FastAPI service | Render Web Service, Free | Serve health/readiness and later `/v1` routes. |
| PostgreSQL | Render Postgres, Free | Temporary MVP/demo data only. |
| Scheduled intelligence rehearsal | Render Cron Job, `0.5c-512mb` (team-approved, min USD 1/month) | Runs `generate-digest --previous-complete-utc-day --limit 5` daily at 06:00 UTC. Its selection window is the previous completed UTC calendar day, and consecutive daily windows have no gap or overlap; `--limit 5` caps each run at five snapshots as a cost control, so the rehearsal is not complete production processing (issue #53). The first execution is triggered manually with the same behaviour. Do not expose the pipeline through a public HTTP trigger. |
| Ad-hoc pipeline runs | Authorised operator's local CLI | Still valid for one-off or debugging runs from an authorised team member's local checkout; never through an unauthenticated public endpoint. |
| Transactional email | Resend, Free | Send confirmation, unsubscribe, and digest test emails over the HTTPS API. |

This selection keeps deployment understandable for a three-person capstone and matches the
existing FastAPI, PostgreSQL, and provider-adapter architecture. It is not a production-readiness
claim.

The repository's `render.yaml` declares the three Free resources needed for the database-backed
MVP — one Free web service, one Free static site, and one Free PostgreSQL database — plus **one
team-approved cron service** (`ai-daily-digest-intelligence`) for the first live
intelligence-pipeline rehearsal. The cron is the only paid resource in the Blueprint; Resend is
still not part of it. See "Intelligence rehearsal cron" below for the approval, schedule,
first-run procedure, and exit-code contract.

## Render foundation

### Service boundaries and configuration

| Intelligence rehearsal cron (`ai-daily-digest-intelligence`) | `pip install uv && uv sync --locked --no-dev --no-editable`; `.venv/bin/generate-digest --previous-complete-utc-day --since 24h --limit 5` (the already-built console script, run directly — not `uv run`) on the `0.5c-512mb` plan, daily at 06:00 UTC. | Resend (later) | HTTPS provider adapter only; not implemented by this foundation | `EMAIL_PROVIDER_API_KEY` (secret), `EMAIL_FROM_ADDRESS` (non-secret sender identity) | Person A owns the remaining Resend provider setup (issue #53, 9 September 2026 handoff). |

`FRONTEND_ORIGIN` is one exact origin such as `https://example.onrender.com`, with no path,
trailing slash, wildcard, credentials, query, or comma-separated alternatives. Non-local HTTP
origins fail configuration validation. CORS allows only this origin, only the currently required
GET/POST methods and headers, and never allows browser credentials. `VITE_API_BASE_URL` is public
build-time configuration and must never contain a secret.

The production factory reads and validates environment variables only when Uvicorn calls it. It
creates one async engine and session factory for the process, mounts `/v1/updates` through a
short-lived session per request, and disposes the engine at shutdown. PostgreSQL is a required
readiness dependency: a failed bounded probe makes readiness return the safe `503` envelope while
liveness continues to describe only the HTTP process.

### Local production-command verification

From a clean checkout on Python 3.12:

```bash
uv sync --locked --no-dev --no-editable
make db-up
make db-migrate
FRONTEND_ORIGIN=http://localhost:3000 \
PAGINATION_CURSOR_SECRET=replace-with-at-least-32-local-bytes \
DATABASE_URL=postgresql+psycopg://ai_daily_digest:ai_daily_digest@localhost:5432/ai_daily_digest \
  .venv/bin/uvicorn ai_daily_digest.delivery.api.production:create_production_app \
  --factory --host 127.0.0.1 --port 8000
```

In a second terminal, verify both probes:

```bash
curl --fail --show-error http://127.0.0.1:8000/v1/health/live
curl --fail --show-error http://127.0.0.1:8000/v1/health/ready
curl --fail --show-error http://127.0.0.1:8000/v1/updates
```

The health bodies are `{"status":"ok"}` and a ready result containing the coarse `database`
check. The updates response contains `items` and `next_cursor`. The committed contract tests also
verify that `render.yaml` points to an importable Uvicorn factory, uses the liveness path, declares
the three Free resources plus exactly the one approved cron service (and no second cron, worker, or
disk), injects both `DATABASE_URL` values by reference, and commits no secret value.

### First deployment

1. Merge only after `make ci` and `cd frontend && npm ci && npm run check` pass on the final branch.
2. In Render, create or sync the Blueprint from the GitHub repository and select `render.yaml`.
   Confirm that the plan shows exactly one Free web service, one Free static site, one Free
   PostgreSQL database, and the one approved cron service `ai-daily-digest-intelligence` on the
   `0.5c-512mb` plan; cancel if it proposes a **second** cron, a worker, a disk, a larger plan,
   or a payment-backed overage.
3. Set `FRONTEND_ORIGIN` to the exact HTTPS static-site origin and `VITE_API_BASE_URL` to the exact
   HTTPS API origin. Render generates `PAGINATION_CURSOR_SECRET`; do not reveal or copy its value.
   Set `ANTHROPIC_API_KEY` only on the cron service (see "Intelligence rehearsal cron").
4. If Render assigns a hostname different from the expected service name, correct both public
   origin values and redeploy. Never relax CORS to a wildcard to work around a mismatch.
5. Confirm the start-script migration succeeded before Uvicorn began accepting traffic. Then confirm
   `/v1/health/live`, `/v1/health/ready`, `/v1/updates`, `/openapi.json`, and the frontend root over
   HTTPS. Confirm an allowed-origin preflight succeeds, a lookalike origin is rejected, and no
   response contains `Access-Control-Allow-Credentials: true`.
6. Record the deployed commit SHA and smoke-test outcome in the issue or PR. Do not record
   environment values, headers, subscriber addresses, or credentials.

### Rollback

1. Select the last known-good deploy for the API and static site in Render, using the same recorded
   commit SHA for both when possible. Do not change or reveal secret values during rollback.
2. If `render.yaml` caused the failure, revert that repository commit through a reviewed PR and let
   the Blueprint reconcile. Do not patch `main` directly.
3. Repeat the HTTPS smoke checks above, including exact-origin CORS and readiness.
4. If a database migration is involved, stop the rollout and follow that migration's documented
   downgrade/forward-fix policy. Prefer a reviewed forward fix; never run a destructive downgrade
   against the only copy of MVP data merely to make a web deploy appear healthy.

### Database deployment gate

Render documents its dedicated pre-deploy command as paid-only. On the Free web service,
`scripts/start_render.sh` therefore applies the reviewed Alembic history before starting Uvicorn;
if migration fails, the HTTP process never starts. This is an MVP compromise, not zero-downtime
migration orchestration. The Free database has no managed backups and expires, so it is demo data
only; export or recreate it through the approved pipeline. Before calling this a production
deployment, ADR 0002 still requires separate migration-owner and restricted runtime roles.
Render's generated Free database credential is not evidence that this role split exists. Record
that gate explicitly and do not weaken database privileges or migration history to make a deploy
pass.

### Intelligence rehearsal cron

**Team approval.** The team explicitly approved **one** Render cron service,
`ai-daily-digest-intelligence`, and its **minimum USD 1/month** charge, so the first live
intelligence-pipeline rehearsal (issue #53) can run on real infrastructure. This supersedes the
earlier "no cron job / zero cost" position for this one service only. Render bills cron services
**by runtime**, so the actual monthly charge can exceed the USD 1 minimum: the team must monitor
the Render **Runs** page for this service and must **not** add a second cron service, raise its
plan, or change its schedule without a new recorded team decision. Person A owns this resource
and its environment values (issue #53, 9 September 2026 handoff).

**Command.** `startCommand` is
`.venv/bin/generate-digest --previous-complete-utc-day --since 24h --limit 5` — the console
script the non-editable build already installed into `.venv`, invoked directly. It is
deliberately **not** `uv run generate-digest`: `uv run` can resynchronize the environment at
runtime and could pull development or editable dependencies into every paid cron execution.

**Schedule and processed day.** `schedule: "0 6 * * *"` — 06:00 UTC daily. Render always
interprets cron schedules in UTC; there is no timezone setting.

`--previous-complete-utc-day` sets the digest date to the **previous completed UTC calendar day**
— the last day that has fully elapsed when the cron fires. It is derived in Python from an
injected, timezone-aware clock (`previous_complete_utc_day`); there is **no shell `date`
expression** in `render.yaml`. It is mutually exclusive with `--digest-date`.

Without this flag, `generate-digest` would default the digest date to the *current* UTC date, and
`--since 24h` would then produce the window `[today 00:00 UTC, tomorrow 00:00 UTC)`. Fired at
06:00 UTC, that window only contains ~6 hours of already-collected data and the following day's
run advances to the next date, so the previous day's 06:00–24:00 interval would be skipped
**permanently**. `--previous-complete-utc-day` fixes that.

**Exact window.** With digest date `D` (the previous completed UTC day) and `--since 24h`,
`resolve_window` produces the half-open window:

```
[ D 00:00:00 UTC ,  D+1 00:00:00 UTC )
```

Example — cron fires at **2026-09-10 06:00 UTC**:

- digest date `D` = **2026-09-09**
- selection window = `[2026-09-09 00:00 UTC, 2026-09-10 00:00 UTC)` — all of 2026-09-09.

**Consecutive windows: no gap, no overlap.** Because each run's window is exactly one calendar
day and the interval is half-open, two consecutive daily runs are contiguous: the run firing on
2026-09-10 06:00 UTC has window `[2026-09-09 00:00, 2026-09-10 00:00)` and the run firing on
2026-09-11 06:00 UTC has window `[2026-09-10 00:00, 2026-09-11 00:00)`, so
`first_window_end == second_window_start == 2026-09-10 00:00 UTC`. No point in time is covered by
two windows or by none.

**Rehearsal `--limit 5` — not complete processing.** `--limit 5` is a deliberate cost control for
this rehearsal on a paid, runtime-billed cron. Each run selects and processes **at most five**
snapshots from its window (ordered by `fetched_at`, then id). The contiguous-window property
above is about the *time range* each run considers; it does **not** mean every snapshot in the
day is processed. A day with more than five snapshots will have the remainder left unprocessed by
this rehearsal — they are not deferred to the next run, which moves on to the next day's window.
Full production processing requires raising or removing `--limit`, which is a separate,
cost-approved change.

**Manual runs behave identically.** A manually **Triggered Run** from the Render Runs page (the
first-run rehearsal, or any later manual run) executes the same `startCommand`, so it also
processes the previous completed UTC day relative to the moment it is triggered — not a partial
"today so far" window — and is subject to the same `--limit 5` cap.

**Scope.** This cron runs the **intelligence pipeline only**. `generate-digest` reads stored
`document_snapshots` and `source_items` within the window, extracts facts, detects changes, and
assembles and gates a digest, then **writes** the resulting `extracted_facts`, `changes`, and
digest/`digest_claims` records through the existing intelligence persistence layer (ADR 0011). It
does **not** collect sources. Combined ingestion-plus-intelligence orchestration is separate
future work and must not be silently added to this service or command — it needs its own issue
and review.

**First-run procedure (first execution is manual):**

1. Merge this change and sync the Render Blueprint from `render.yaml`.
2. In the Blueprint diff, confirm Render proposes **only** the existing API web service, the
   static frontend, the PostgreSQL database, and the one new cron service
   `ai-daily-digest-intelligence`. Cancel if it proposes a second cron, a worker, a disk, a
   larger plan, or any other paid resource.
3. The Blueprint sync **creates** the cron service. Immediately open it and set
   `ANTHROPIC_API_KEY` manually in its Render environment. Enter the value only in the dashboard;
   never commit, echo, or paste it into an issue, PR, or log.
4. Do **not** open, copy, or expose `DATABASE_URL` — Render injects it automatically from the
   database's `connectionString` and it must stay only in Render.
5. **Only after `ANTHROPIC_API_KEY` is configured**, trigger the first run from the service's
   **Runs** page with **Trigger Run**. Do not wait for 06:00 UTC for the rehearsal — a manual run
   processes the previous completed UTC day just like the scheduled run (see "Manual runs behave
   identically" above).
6. Capture only the **final single-line JSON `DigestRunReport`** printed to stdout and the
   **process exit code**. Record those in issue #53 / the PR.
7. Do **not** share raw logs, prompt text, database credentials, connection strings, or API
   keys. The report line is safe to share; the surrounding log output is not.

**Expected exit codes** (`generate-digest`):

| Exit code | Meaning |
|---|---|
| `0` | Digest published. |
| `1` | Digest routed to review, or a partial run (some snapshots failed). |
| `2` | Run failed / could not start (e.g. database unreachable, bad arguments). |

A `review` / `partial` outcome (exit `1`) is a **valid rehearsal result**, not a failure to fix
by loosening the pipeline. The pipeline's publication and safety gates are not to be weakened to
make the rehearsal publish.

## Render free-tier constraints

Render documents the current free allowances and limitations in
[Deploy for Free](https://render.com/docs/free):

- Static Sites are free, subject to the workspace's included bandwidth and build-pipeline usage.
- A workspace receives 750 free web-service instance hours per calendar month.
- A free web service spins down after 15 minutes without inbound traffic. Its next request can be
  delayed while the service starts again.
- Free web services have an ephemeral filesystem and cannot attach a persistent disk.
- Free web services cannot make outbound SMTP connections on ports 25, 465, or 587. Email delivery
  must therefore use Resend's HTTPS API, not SMTP.
- Only one free Render Postgres database can be active per workspace. It has 1 GB of storage, no
  backups, no managed connection pooling, and expires 30 days after creation. After the documented
  14-day upgrade grace period, Render deletes it.
- Render may restart or maintain free services and databases at any time. The free plans are for
  preview and hobby use, not production availability.

Render [Cron Jobs](https://render.com/docs/cronjobs) are billed by runtime and have a minimum
monthly charge of USD 1 per cron service. The team has **accepted that cost for exactly one cron
service**, `ai-daily-digest-intelligence`, to run the intelligence-pipeline rehearsal (see
"Intelligence rehearsal cron" above). Runtime billing can exceed the USD 1 minimum, so the team
monitors this service's Runs page. Any **additional** cron service, a worker, a plan increase, or
a schedule change still requires a new recorded team decision. All other scheduled or ad-hoc
pipeline work stays on an authorised operator's local CLI.

### Render operating rules for the MVP

1. Select `free` explicitly for the web service and PostgreSQL; do not rely on dashboard defaults.
2. The only approved paid resource is the single `ai-daily-digest-intelligence` cron service on
   the `0.5c-512mb` plan. Do not create a second cron service, a worker, a disk, a larger
   database, or any other paid resource without a recorded team decision.
3. Trigger the intelligence rehearsal through the approved cron service's Runs page (manual
   first run). Ad-hoc or debugging pipeline runs may still be run from an authorised team
   member's local checkout with values supplied through that operator's untracked local
   environment; never expose the command through an unauthenticated public endpoint.
4. Warm the API with a health request shortly before a live demonstration, while still treating
   cold-start behavior as expected rather than masking readiness failures.
5. Export through an approved migration process or move to durable PostgreSQL before the 30-day
   expiry. The free database is not the long-term system of record promised by ADR 0002.
6. Keep the application stateless outside PostgreSQL; never rely on Render's local filesystem.

### Manual pipeline execution boundary

The daily intelligence rehearsal now runs on the approved Render cron service
(`ai-daily-digest-intelligence`), triggered from Render's Runs page. Outside that one service, an
authorised team member still runs the documented collection/digest CLI command from a local
repository checkout for ad-hoc or debugging work, supplying deployment configuration through an
untracked local environment and monitoring the command directly. Neither path is an API route:
the command must not be wrapped in or exposed through an unauthenticated public HTTP endpoint. Any
**public or remote HTTP** trigger — as opposed to Render's own authenticated scheduler and Runs
page — still requires a separate security decision covering authentication, authorisation, replay
protection, rate limits, audit logging, and secret access.

#### Controlled historical-article rehearsal

After the official-article backfill change is merged and the existing
`ai-daily-digest-intelligence` cron service shows that exact `main` commit as
its latest successful build, an authorised operator may create a **one-off
job on that existing service** with this command:

```bash
.venv/bin/collect-official-article --source-id anthropic_news --url https://www.anthropic.com/news/100k-context-windows --url https://www.anthropic.com/news/claude-2-1
```

This does not change the cron's configured start command or schedule and must
not create another Render service. The pages are intentionally supplied oldest
first: Anthropic's 11 May 2023 100K context-window announcement establishes the
baseline, followed by its 21 November 2023 Claude 2.1 200K announcement. The
data remains real first-party evidence; no facts are pasted or synthesised.

Record only the command's final secret-safe JSON line and exit status. A clean
first run should report `status: ok`, `requested_count: 2`,
`processed_count: 2`, and two created snapshots; an idempotent rerun may instead
report them unchanged. If collection succeeds, copy the report's `started_at`
value and create a second one-off job on the same service:

```bash
.venv/bin/generate-digest --since <article-report-started_at> --limit 5 --digest-date <current-UTC-date>
```

Success for the full rehearsal means the intelligence report contains a
grounded change and claim, the publication gates allow a published digest, and
the stored result appears through `/v1/changes`, `/v1/digests`, and the UI. A
draft or review-required outcome is still a valid fail-closed result and must
be investigated from its safe reason codes; never weaken the gates merely to
force a demonstration.

## Resend free-tier constraints

Resend's current [pricing](https://resend.com/pricing) and
[quota documentation](https://resend.com/docs/knowledge-base/account-quotas-and-limits) list:

- 3,000 transactional emails per month;
- 100 transactional emails per day;
- three verified domains on the Free plan;
- 30 days of activity-data retention; and
- no free-plan overage. Sending pauses when the free allowance is exhausted.

Each `To`, `CC`, or `BCC` recipient counts separately. The MVP must therefore test only with the
three approved team recipients or Resend's documented
[test addresses](https://resend.com/docs/dashboard/emails/send-test-emails), and it must not send to
a real subscriber list.

Resend requires an API key for the HTTPS API. Create a sending-only, domain-restricted key where
possible and store it only in the deployment secret environment. Resend displays a newly created
key once, so the key owner must record and rotate it through the agreed secret-management process.
See [Resend API keys](https://resend.com/docs/dashboard/api-keys/introduction).

Sending to recipients beyond the account's restricted test case requires a domain the team owns.
The DNS owner must publish and verify the SPF and DKIM records described in
[Managing Domains](https://resend.com/docs/dashboard/domains/introduction). Domain registration is
separate from Resend and may introduce a cost if the team does not already own one.

### Resend operating rules for the MVP

1. Use the HTTPS email API, never SMTP from the Render service.
2. Use the provider adapter required by the architecture; domain logic must not import a Resend SDK.
3. Keep an application-side daily safety limit below the provider's 100-message cap.
4. Preserve delivery idempotency so retries cannot consume the quota or send duplicate messages.
5. Log provider message identifiers and safe status metadata, never raw tokens or subscriber email
   addresses.
6. Use team/test recipients until the domain, consent, confirmation, unsubscribe, and suppression
   paths have passed their tests.

## Alternatives considered

The existing boundaries keep these providers replaceable. An alternative should still expose
PostgreSQL through `DATABASE_URL`, run the FastAPI ASGI service, use environment-backed secrets,
and sit behind the delivery email adapter.

approved compatibility decision. ADR 0002 remains authoritative for the storage model regardless
of host.

## Upgrade triggers

The team must revisit the provider decision before any of these events:

- the API must remain responsive without free-tier cold starts;
- PostgreSQL data must remain available beyond the 30-day MVP window or require backups;
- automated scheduling beyond the single approved intelligence-rehearsal cron is required (for
  example a second cron for ingestion, or ingestion-plus-intelligence orchestration);
- expected transactional email exceeds 100 recipients per day or 3,000 per month;
- a real subscriber list replaces controlled team/test recipients;
- availability, support, audit, data-retention, or recovery requirements become production-grade;
- a provider asks for a payment method or enables usage-based overages.

At that point, record the expected monthly cost, owner, spending cap, rollback/export path, and
non-author approval before enabling the paid resource.

The remaining pending row (Resend sending domain / DNS ownership) is an operational gate, not a
reason to commit guessed values: no general-recipient email send may proceed past it. The
intelligence cron follows the first-run procedure above: the Blueprint sync **creates** the cron
service, Person A then **immediately sets `ANTHROPIC_API_KEY`** in that service's Render
environment, and only after the key is configured is the first execution **manually triggered**.
`DATABASE_URL` needs no manual step — Render injects it automatically from the database. The first
run's result is recorded on issue #53.

Subscription activation has two additional fail-closed gates under ADRs 0012 and 0013. Person A
must wire a provider-neutral confirmation-delivery adapter so the raw confirmation capability is
passed directly to the provider after the database transaction and is never returned, persisted,
or logged. Person A must also configure Uvicorn/Render with an explicit trusted-proxy allowlist and
verify that `request.client` contains the validated public client address; wildcard proxy trust is
not allowed. Until both conditions are reviewed and tested under issue #53, the production factory
keeps all subscription routes unmounted even when subscription security keys are present.
The static frontend likewise keeps `VITE_SUBSCRIPTIONS_ENABLED` false or unset until those gates
are complete, so production does not display controls backed by an unavailable endpoint.
