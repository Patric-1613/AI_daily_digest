# 0012 — Subscription confirmation and unsubscribe token security

Status: Accepted by Person A (Patric, 2026-09-04), Person B (Sujin, 2026-09-04), and Person C
(author) via PR #51
Date: 2026-09-04
Issue: [#50](https://github.com/Patric-1613/Virtusa_CaPStone/issues/50)

## Context

AI Daily Digest uses double opt-in for subscriptions and must let a recipient unsubscribe without
an account or authenticated browser session. Both actions are bearer-capability flows: possession
of the emailed link is the proof that the caller controls the mailbox. A weak, reusable, leaked, or
mis-scoped token could confirm an address without consent, unsubscribe another reader, disclose
whether an address is registered, or expose subscriber data through logs and analytics.

The existing project contract already requires:

- `POST /v1/subscriptions` to return the same privacy-preserving response whether an address exists;
- confirmation and unsubscribe to accept signed, single-purpose tokens;
- raw tokens never to be stored;
- token purpose, hash, expiry, and use/revocation time to be stored;
- UUIDs not to be used as security tokens (ADR 0007); and
- unsubscribe tokens to be hashed at rest and links to be expiring or revocable
  (`docs/ARCHITECTURE.md`).

This ADR makes those requirements implementable. It decides token construction, storage and
lifecycle semantics, browser and one-click behavior, concurrency, key rotation, logging, and the
boundary between the public API, frontend, persistence, and email adapter. It does not implement
subscriptions, email sending, persistence, or routes.

The controls follow the transferable URL-token guidance in the
[OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html):
use a cryptographically secure generator, sufficient entropy, secure storage, purpose binding,
expiry/single use where appropriate, HTTPS links built from a trusted origin, enumeration-resistant
responses, and rate limiting. Confirmation and unsubscribe are not password-reset flows, but they
share the same bearer-token threats.

## Decision

### 1. Token format and cryptography

Confirmation and unsubscribe tokens use the same versioned envelope but are different purposes:

```text
v1.<key_id>.<purpose>.<random>.<signature>
```

- `purpose` is exactly `confirm_subscription` or `unsubscribe`. Delivery represents this
  application-owned closed set with a module-local standard-library `StrEnum`, following
  [ADR 0009](0009-shared-enum-policy.md); the persisted column has the equivalent two-value check.
- `random` contains 32 bytes (256 bits) generated by Python's
  [`secrets`](https://docs.python.org/3/library/secrets.html) module and encoded as unpadded,
  URL-safe base64.
- `signature` is HMAC-SHA-256 over the exact ASCII bytes of
  `v1.<key_id>.<purpose>.<random>`, using the key selected by `key_id`. Its 32-byte digest is
  encoded as canonical, unpadded, URL-safe base64: exactly 43 ASCII characters.
- Signature comparison uses
  [`hmac.compare_digest`](https://docs.python.org/3/library/hmac.html), never ordinary string
  equality.
- The parser applies a small fixed maximum token length, requires the exact five-segment format,
  rejects unknown versions, key IDs and purposes, and rejects non-canonical base64 before database
  work.
- Tokens contain no email address, subscription ID, consent timestamp, delivery ID, or other
  personal or business data. `key_id` and `purpose` are non-secret routing values.
- Tokens are not UUIDs, JWTs, encrypted subscriber records, or values created by `shared.ids.new_id()`.

The signature authenticates the version and purpose before the token is used as a capability. The
random component supplies unguessability. Database state supplies expiry, revocation, single-use,
and lifecycle control; the signed envelope is not treated as a stateless authorization decision.

No new production dependency is required. Python's standard-library `secrets`, `hmac`, `hashlib`,
and `base64` modules provide the required primitives.

### 2. Storage model and data minimization

The later Delivery-owned subscription migration stores token records with at least:

| Field | Rule |
|---|---|
| `id` | Internal UUID v7 resource ID; never used as the bearer token. |
| `subscription_id` | `UUID NOT NULL` foreign key to the subscriber record with `ON DELETE RESTRICT`, preserving suppression and consent audit history. |
| `purpose` | Closed value: `confirm_subscription` or `unsubscribe`. |
| `token_digest` | Unique SHA-256 digest of the complete ASCII token. |
| `key_id` | Signing-key version used to verify the envelope. |
| `consent_generation` | `INTEGER NOT NULL`; identifies the subscription lifecycle that issued the token. Subscription rows start at `DEFAULT 1` and increment atomically for every re-subscription lifecycle. Token rows copy the current value explicitly and have no default, preventing accidental fallback to generation 1. |
| `created_at` | Server-generated UTC timestamp. |
| `expires_at` | Required for confirmation; nullable for revocable unsubscribe tokens. |
| `used_at` | First successful use, if any. |
| `revoked_at` | Explicit invalidation time, if any. |

Only `token_digest` is persisted for lookup. The raw token may exist in process memory only long
enough to construct the outbound HTTPS link and submit the email-provider request. It is never
written to a database, cache, file, queue payload, metric, trace, exception, or log.

Subscriber email addresses are stored only in the subscription record. Token records, delivery
records, and operational logs use internal IDs. Logs record the route template, request ID, safe
outcome category, and anonymized subscription ID where needed; they never record request bodies,
raw tokens, query strings, full URLs, or email addresses.

The subscription-persistence ADR must set the exact bounded retention interval for terminal token
rows before its migration is accepted. The following limits already apply:

- active or used unsubscribe-token rows for the current consent generation remain available so
  links in delivered mail keep working and successful retries stay idempotent;
- superseding a consent generation or explicitly revoking it makes its unsubscribe-token rows
  eligible for deletion only after the documented security/audit interval;
- expired, used, or revoked confirmation-token rows are eligible for deletion after that same
  interval; and
- cleanup is a scheduled, idempotent database operation. It never substitutes deletion for first
  recording expiry, use, or revocation, and it never deletes the subscription-level consent and
  suppression audit record.

### 3. Confirmation lifecycle

1. `POST /v1/subscriptions` validates the request and explicit consent flag, then always returns the
   existing generic response. It does not reveal whether the normalized address already exists,
   is pending, confirmed, suppressed, or unsubscribed.
2. A confirmation token is scoped to `confirm_subscription` and the current
   `consent_generation`. Its default lifetime is 24 hours and is configurable only within a
   reviewed bounded policy.
3. Repeated eligible subscribe requests may issue multiple confirmation tokens. Confirming any one
   valid token atomically confirms that consent generation and revokes its remaining confirmation
   tokens. This avoids invalidating an already-delivered email when a later provider attempt has an
   uncertain result.
4. Confirmation is a state-changing POST. The transaction locks the token and subscription rows,
   rechecks purpose, digest, signature, generation, expiry, `used_at`, and `revoked_at`, then records
   confirmation and token consumption in one commit.
5. A consumed, expired, revoked, malformed, tampered, wrong-purpose, or wrong-generation token makes
   no state change and returns HTTP 400 through the standard error envelope with code
   `invalid_subscription_token`, message `"The subscription token is invalid or no longer usable."`,
   and empty `details`. Every unusable-token case has the same status and public body and exposes no
   email or subscription state. The UI may offer a new confirmation email without echoing the
   submitted address.
6. Re-subscribing after unsubscribe creates a new pending consent generation and requires a new
   double-opt-in confirmation. Old tokens cannot reactivate or alter the new consent generation.

Confirmation tokens are single use. Concurrent attempts serialize on the stored token/subscription;
exactly one transaction performs the transition and subsequent attempts are harmless.
A request body that fails JSON/schema validation remains the existing HTTP 422 `validation_error`;
the HTTP 400 rule above applies after a token string has passed request-schema validation.

### 4. Unsubscribe lifecycle

- Unsubscribe tokens are scoped to `unsubscribe` and one confirmed `consent_generation`.
- They are revocable rather than short-lived. This keeps links in delivered digest emails useful
  without allowing an old consent generation to control a later re-subscription.
- A new consent generation, key-compromise response, or explicit administrative suppression revokes
  the relevant outstanding tokens.
- A valid unsubscribe request atomically changes the subscription to unsubscribed, records the
  server UTC time, and cancels or suppresses unsent deliveries. It does not erase delivery audit
  records required for idempotency and suppression.
- Unsubscribe is idempotent: retrying a valid token after the first success returns the same generic
  success response and never re-subscribes, sends mail, or leaks prior state. `used_at` records the
  first successful use.
- A malformed, expired, revoked, tampered, wrong-purpose, wrong-generation, or otherwise unusable
  unsubscribe token returns the same HTTP 400 `invalid_subscription_token` envelope defined for
  confirmation. A correctly signed token already used to complete that same unsubscribe remains an
  idempotent generic success rather than becoming an error.
- Unsubscribe never requires login, cookies, HTTP authorization, or knowledge of the email address.

If a suppression rule is stricter than ordinary unsubscribe (for example, a hard bounce or abuse
complaint), a confirmation token cannot override it. The future persistence ADR must define the
subscription/suppression state machine before implementation.

### 5. Browser links and state-changing methods

Automated mail scanners and link-preview tools commonly fetch links. A GET request must therefore
never confirm or unsubscribe a reader.

- Human-facing GET links render a minimal confirmation page only. The page performs the action
  through an explicit POST after user intent.
- Token-bearing pages send `Cache-Control: no-store` and a strict `Referrer-Policy: no-referrer`,
  contain no third-party scripts, images, analytics, or links, and do not place the token into
  client-side telemetry.
- Email links are built from one configured, allowlisted HTTPS public origin. They are never built
  from an inbound `Host` or forwarded-host header.
- Success responses do not redirect to a token-bearing URL. After a browser POST, the server or
  frontend replaces token-bearing history before showing a safe result page.

The current JSON request contract for `POST /v1/subscriptions/confirm` and
`POST /v1/subscriptions/unsubscribe` remains a design target. Exact human-facing GET routes and any
frontend-to-API handoff must be added to `docs/API_CONTRACT.md` and generated OpenAPI in the later
implementation PR, following ADR 0010. This ADR does not add placeholder routes.

These browser actions are credentialless bearer-capability requests: they set and accept no session
or authentication cookie, send no HTTP authorization credential, and do not rely on `SameSite` for
security. A cross-site page cannot obtain or ambiently attach the token, so traditional cookie-based
CSRF does not apply. The browser-facing JSON POST routes nevertheless fail closed unless the
request's `Origin` exactly matches the configured first-party HTTPS frontend origin. Their CORS
policy allows that exact origin, `POST`, and the required JSON content headers only, sets
`allow_credentials` to false, and never uses a wildcard origin. `Referer` is neither required nor
treated as authentication; token-bearing pages already suppress it with `no-referrer`.

The RFC 8058 endpoint is a separate provider-facing form POST. It must accept requests without
browser `Origin` or `Referer` headers and is not added to the browser CORS allowlist. Its protection
is the single-purpose bearer token, exact RFC form value, rate limit, and idempotent state transition,
not cookies or browser headers. This endpoint separation, CORS configuration, and public behavior
must be reflected in the later API contract and OpenAPI implementation, completing ADR 0010's
deferred CORS decision for this feature only.

### 6. RFC 8058 one-click unsubscribe

Digest email should support [RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html) separately from
the human confirmation page:

- email contains a `List-Unsubscribe` header with one configured HTTPS URI carrying the opaque
  unsubscribe token;
- email contains `List-Unsubscribe-Post: List-Unsubscribe=One-Click`;
- the DKIM signature covers both headers;
- the one-click endpoint accepts the RFC-defined POST form value, requires no cookie or HTTP
  authorization, performs the idempotent unsubscribe, returns a direct success response, and never
  redirects; and
- a GET to that URI does not mutate state.

The Resend adapter must prove that the selected API supports setting and DKIM-signing these headers
before one-click support is advertised. If the provider cannot satisfy RFC 8058, the application
still sends a visible human unsubscribe link, and the limitation is recorded rather than claiming
standards compliance.

### 7. Keys, rotation, and configuration

- Signing keys are high-entropy secrets supplied through environment configuration or an approved
  secret manager. `.env.example` contains names with empty values only.
- Confirmation and unsubscribe use separate purpose-specific key IDs and key material; a key is
  never reused across the two purposes. One key ID per purpose is active for issuance.
- Retired confirmation keys remain verification-only until every token they signed has expired or
  been revoked. Retired unsubscribe keys remain verification-only while any token they signed still
  belongs to the current consent generation, including a used token retained for idempotent replay.
  They may be removed after those generations are superseded/revoked and the token-row retention
  interval has elapsed.
- Unknown or removed key IDs fail closed. Removing a compromised key immediately revokes every
  token signed by it; this incident-response override takes precedence over normal retention and
  intentionally invalidates affected unsubscribe links.
- Rotation changes the active key ID without silently changing token format version.
- Production, staging, development, and test use disjoint signing-key material and disjoint `key_id`
  namespaces. Startup rejects a key ID outside the configured environment namespace, so a token
  issued in one environment can never validate in another.
- Startup/configuration validation rejects duplicate key IDs, an absent active key, weak/empty key
  material, key reuse across purposes, or an active key not present in the verification ring.
- Secrets and configuration values never appear in readiness output, OpenAPI metadata, logs, or
  exceptions.

The implementation must document an operational rotation procedure before production email is
enabled.

### 8. Abuse controls and privacy-preserving responses

- Apply bounded per-address and per-network rate limits to subscription and confirmation-email
  issuance. Address-based limit keys use a keyed digest, not a plaintext email in the rate-limit
  store or logs.
- Apply a separate request-rate limit and strict token-length limit to confirm and unsubscribe
  endpoints. Rate limiting supplements token entropy; it does not replace cryptographic validation.
- Subscribe responses have the same status, body, and materially similar processing path for known
  and unknown addresses.
- Token endpoints never return the associated email, subscription ID, consent generation, token
  state, or precise validation failure. Internal logs may use coarse outcomes such as `invalid`,
  `expired`, `revoked`, `replayed`, and `accepted` with an internal request ID.
- Subscriber addresses and tokens never appear in URL query logging, analytics, exception trackers,
  or provider metadata beyond the recipient field required to send the email.

Rate-limit thresholds and retention of network-derived limit keys are deployment configuration and
must be documented in the implementation PR. Tests use deterministic fakes and make no provider or
network calls.

### 9. Transaction and email-send boundaries

- Creating subscription/token state commits before an email send is attempted. Database
  transactions never remain open across a provider network call.
- The confirmation-email delivery record uses a stable idempotency key. Provider timeout or unknown
  outcomes follow the email delivery retry policy; they do not log or persist the raw token.
- Multiple outstanding confirmation tokens are permitted as described above, so a later retry does
  not make an already-delivered confirmation link invalid.
- Unsubscribe updates and suppression of unsent deliveries occur in one database transaction.
  Workers recheck subscription eligibility immediately before sending, so a queued job cannot send
  after a committed unsubscribe.
- Provider webhooks are a separate authenticated input. Their signature verification, replay
  defense, event idempotency, and bounce/complaint behavior require a later provider-adapter
  decision and are not delegated to these subscriber bearer tokens.

## Required implementation tests

The later implementation PR must include tests proving:

1. generated random components contain 256 bits, signatures are canonical 43-character unpadded
   URL-safe base64, and complete tokens are URL-safe and bounded;
2. malformed, oversized, non-canonical, wrong-version, wrong-key, wrong-purpose, wrong-generation,
   expired, revoked, consumed confirmation, and tampered tokens fail closed without a database
   mutation and return the same HTTP 400 `invalid_subscription_token` envelope; request-schema
   failures remain HTTP 422;
3. signature comparison uses the central verifier and no alternate parser bypasses it;
4. persisted rows contain the token digest but never the raw token, token rows explicitly copy an
   integer consent generation, and deleting a referenced subscription is rejected by `ON DELETE
   RESTRICT`;
5. persisted rows and captured logs, traces, errors, and metrics contain no raw token or subscriber
   email; provider fakes may inspect the outbound message transiently but never persist, snapshot,
   or log its recipient or token-bearing link;
6. subscription initiation returns the same public response for unknown, pending, confirmed,
   suppressed, and unsubscribed addresses;
7. confirmation expiry, single-use behavior, generation binding, concurrent consumption, and
   revocation of sibling confirmation tokens are correct; subscription generation starts at 1,
   increments atomically on re-subscription, and token issuance cannot silently default to an old
   generation;
8. unsubscribe is idempotent, requires no session, suppresses unsent delivery, and cannot affect a
   newer consent generation;
9. GET requests and link previews never mutate confirmation or subscription state;
10. links use only the configured HTTPS origin and ignore hostile `Host`/forwarded-host values;
11. token-bearing responses use `no-store` and `no-referrer` and include no third-party resources;
12. key rotation verifies retained purpose-specific keys, issues only with each purpose's active
    key, retains unsubscribe verification keys while current-generation links remain usable, and
    fails closed after an intentional key removal; tokens and key IDs from every other environment
    fail validation;
13. rate limiting does not store/log plaintext addresses and cannot be bypassed by response-state
    differences;
14. RFC 8058 POST handling requires the exact one-click form value, is idempotent, needs no cookies
    or authorization, does not redirect, and GET remains non-mutating; and
15. email-send retries and unsubscribe/send races do not produce mail after committed suppression;
16. token cleanup preserves current-generation unsubscribe replay, removes only eligible terminal
    rows after the configured audit interval, and retains subscription-level consent/suppression
    history; and
17. browser confirmation/unsubscribe rejects absent or non-allowlisted origins, emits no cookies,
    uses credentialless exact-origin CORS, and does not rely on `Referer` or `SameSite`, while the
    separate RFC 8058 POST continues to work without browser origin headers.

Integration tests use a fake email adapter. A separate controlled test against Resend test
recipients is required before production enablement; real subscriber lists are out of scope.

## Consequences

- A database leak does not reveal usable bearer tokens because only high-entropy token digests are
  stored.
- Purpose binding prevents a confirmation token from being accepted as an unsubscribe token or the
  reverse.
- Stored server-side state makes single use, revocation, consent-generation isolation, and key
  compromise response explicit; the system cannot be implemented as stateless signed links alone.
- POST-only mutations prevent mail scanners and previews from silently changing subscription state.
- Multiple outstanding confirmation tokens and idempotent unsubscribe make retries safe, at the
  cost of additional short-lived token rows.
- Key rotation requires purpose- and environment-specific verification key rings and an operational
  process; unsubscribe verification keys can be long-lived while their consent generations remain
  current.
- The later subscription schema, API/OpenAPI changes, frontend pages, email adapter, and deployment
  configuration must implement this decision together rather than inventing token behavior in
  separate PRs.

## Rejected alternatives

- **UUID v4/v7 token:** uniqueness is not a security proof; ADR 0007 explicitly excludes UUIDs.
- **Unsigned random token only:** a database digest would still make a strong opaque capability,
  but it would not authenticate version and purpose before lookup and would contradict the accepted
  signed-token contract.
- **Stateless JWT or signed payload containing email/subscription data:** complicates revocation and
  single use, exposes decodable metadata, and adds no benefit for a database-backed workflow.
- **Plaintext token storage:** turns a database read into immediate subscriber-action capability.
- **State-changing GET:** vulnerable to link scanners, previews, browser prefetch, and accidental
  clicks.
- **Short-lived unsubscribe only:** makes older delivered mail harder to leave. Revocation tied to
  consent generation provides the required control without a short expiry.
- **Building links from request host headers:** permits host-header injection into security emails.
